# 03. ステージ JSON 仕様とステージ追加手順

対象: [src/game/stage/stages/](../src/game/stage/stages/) 配下の `*.json`。
パーサの実装は [stage.ts:66-150](../src/game/stage/stage.ts#L66-L150)。

## 1. スキーマ

```jsonc
{
  "steps": 5,          // 省略可（既定 4）。1 ループで動ける回数
  "tiles": [           // 必須。1 要素 = 1 行。文字の位置がそのまま x 座標
    "  a#",
    "S###",
    " G  "
  ],
  "objects": [         // 省略可
    {
      "type": "laser",           // 現状 "laser" のみ。未知の type は黙って無視される
      "id": "a",                 // 同じ文字の SwitchTile で無効化できる
      "position": { "x": 1, "y": 1.5 }   // 片方が .5 の半整数
    }
  ]
}
```

TypeScript の型はまだ存在しない（`any` で読んでいる）。
型を付ける作業は [07-roadmap.md](07-roadmap.md) のフェーズ 1。

## 2. `tiles` の書き方

### 座標系

- **原点は左上。** `x` = 行内の文字位置（0 始まり）、`y` = 配列のインデックス（0 始まり）。
- 行の長さは揃っていなくてよい。足りない分はタイル無しとして扱われる。

### 使える文字

| 文字 | 意味 |
|---|---|
| `S` | スタート（**必須・1 個**）。ここにプレイヤーが出現する |
| `G` | ゴール |
| `#` | 通常タイル |
| `@` | 最初から通過済みのタイル（＝進入できない障害物） |
| `a`〜`z` | スイッチタイル。文字が ID になる |
| 半角スペース | タイル無し |
| その他の文字 | タイル無し（無視される）。ただし**小文字は必ずスイッチになる**ので注意 |

### 制約（守らないと壊れる / 崩れる）

1. **`S` は必ず 1 個入れる。** 無いとプレイヤー生成時にクラッシュする
   （[stage.ts:128](../src/game/stage/stage.ts#L128) で `start!` が `undefined` になる）。
   複数書いた場合は最後に見つかったものが採用される。
2. **`y = 0` の行と `x = 0` の列に、それぞれ最低 1 個はタイルを置く。**
   センタリング計算が `aabb.min` を 0 と仮定しているため、
   左や上に空きがあるとその分だけフィールドが右下にずれる
   （[field.ts:62-65](../src/game/stage/field.ts#L62-L65)、詳細は [06-known-issues.md の F-1](06-known-issues.md)）。
   → **必ず左詰め・上詰めで書く。**
3. **サイズ上限**: `gap = 60px`、画面 1280x720。
   幅は 21 列、高さは 12 行が物理的な限界。**余白を考えて 18 列 x 10 行以内**を推奨。
4. タイルが 1 個しかないステージは作らない
   （`StageView` の `manhattan.max - manhattan.min` が 0 になり 0 除算する）。

## 3. `objects` の書き方

### laser

```jsonc
{ "type": "laser", "id": "a", "position": { "x": 7.5, "y": 0 } }
```

- **`position` は必ず片方だけ `.5`。** 両方整数だとタイルの真上に乗って判定されない。
  両方 `.5` だと当たり判定のキーと一致せず機能しない。
- `x` が `.5` → タイル `(floor(x), y)` と `(ceil(x), y)` の**間**を塞ぐ（横方向の通行止め）。
- `y` が `.5` → タイル `(x, floor(y))` と `(x, ceil(y))` の**間**を塞ぐ（縦方向の通行止め）。
- `id` に対応する `SwitchTile`（同じ文字）が `tiles` に無い場合、そのレーザーは**永久に消せない壁**になる。
  意図的に使ってよい（現状は全ステージで対応スイッチを置いている）。
- 複数のレーザーに同じ `id` を付ければ、1 つのスイッチでまとめて消せる。

> 見た目の向き（`vertical`）は `Math.round(y) === y` で自動決定される。手で指定する項目は無い。

### type を増やしたい場合

[stage.ts:107-117](../src/game/stage/stage.ts#L107-L117) の `switch(v.type)` に分岐を足す。
手順は [04-recipes.md](04-recipes.md#レシピ-b-新しいオブジェクトギミックを追加する) を参照。

## 4. ステージの追加手順

### 4.1 ロード順の罠

ステージは `import.meta.glob('./stages/*.json', { eager: true })` で読み込まれ、
`Object.values()` の順＝**ファイル名の辞書順**がそのままステージ順になる
（[stage.ts:13](../src/game/stage/stage.ts#L13)）。

```
stage1.json, stage10.json, stage2.json, stage3.json, ...   ← 辞書順ではこうなる
```

**`stage10.json` を作った瞬間、ステージ 2 の位置に割り込む。**

| 状況 | やること |
|---|---|
| 9 ステージ目まで | `stage8.json`, `stage9.json` を素直に追加してよい |
| 10 ステージ目以降 | **先に [07-roadmap.md](07-roadmap.md) フェーズ 1 の「明示的なステージ index 化」を実施する。**<br>暫定対応するなら全ファイルを `stage01.json` 形式のゼロ埋めにリネームする |

### 4.2 手順

1. `src/game/stage/stages/stageN.json` を作る（N は連番）。
2. §2 / §3 の制約を守って `tiles` と `objects` を書く。
3. **手で解けるか確認する**（§5 のチェックリスト）。
4. `bun run dev` で起動。前のステージまで手動で進めるのが面倒なら、
   [title.ts:69](../src/game/title/title.ts#L69) の `s.load(0)` を一時的に `s.load(N-1)` に変えて確認し、**戻す**。
5. `./node_modules/.bin/tsc --noEmit` を通す（JSON 追加だけなら通るはず）。

### 4.3 ファイルサイズの落とし穴

`stage.ts` は `currentData.tiles` のように **JSON の名前付きエクスポート**を読んでいる。
Vite は既定（`json.stringify: 'auto'`）で **10KB を超える JSON を `JSON.parse` 化し、名前付きエクスポートを止める**。
その瞬間 `currentData.tiles` が `undefined` になり、**ビルド版だけ**壊れる。

→ **1 ステージの JSON は 10KB 未満に収めること。** 大きくなるならデータ構造を見直す。

## 5. ステージ設計チェックリスト

作ったステージについて、以下を頭の中（またはメモ）で追うこと。

- [ ] `S` が 1 個ある。`G` がある。
- [ ] `x=0` の列と `y=0` の行にタイルがある（左詰め・上詰め）。
- [ ] 幅 18 列 x 高さ 10 行以内。
- [ ] レーザーの `position` は片方だけ `.5`。
- [ ] レーザーの `id` に対応するスイッチが（意図しない限り）ある。
- [ ] **ループ 1 で何をさせたいか**が明確（歩数を使い切る / スイッチに乗る / 特定の位置で終わる）。
- [ ] **ループ 2 のゴーストの経路と実体歩数**を計算した（§6）。
- [ ] その結果、ゴールに到達する手順が実在する。
- [ ] 一筆書きの制約上、意図しない近道が無い。
- [ ] 詰み判定はレーザーを見ない（[02-game-rules.md §6](02-game-rules.md#6-詰み判定-isjammed)）ことを前提にしている。

## 6. ゴーストを見積もる手順

ステージ設計で最も間違えやすいのがここ。次の順で計算する。

1. ループ 1 でプレイヤーに歩かせたい経路を決める。移動回数を `u`、`steps` を `n` とする。
2. 余り歩数 `r = n - u`。ただし歩数を使い切る前に詰みやレーザーで終わる場合は、その時点の残数。
3. **次のループのゴースト**は:
   - 出発位置 = ループ 1 の**終点**
   - 経路 = ループ 1 の軌跡を**逆向きに**辿り、`S` に向かう（長さ `u` 歩）
   - **実体でいるのは、出発タイルを含めて `r` タイル分**
   - プレイヤーが 1 歩動くごとにゴーストも 1 歩動く（同期）
4. ゴーストが実体でいる `r` タイルが、ループ 2 のプレイヤーの通り道と衝突しないか（させたいか）を確認する。

```
例: steps=6、ループ1で 4 歩使って終わった場合
  r = 2 → ゴーストは「終点」と「終点の 1 つ手前」の 2 タイルだけを塞ぐ。
          残り 2 歩ぶんは半透明のまますり抜ける（ただしスイッチは押す）。
```
