# 03. ステージ JSON 仕様とステージ追加手順

対象: [src/game/stage/stages/](../src/game/stage/stages/) 配下の `*.json`。
パーサの実装は [stage.ts](../src/game/stage/stage.ts) の `reset()`、
文字 → タイルの対応は [tiles.ts](../src/game/stage/tiles.ts) の `tileRegistry`。

## 1. スキーマ

```jsonc
{
  "steps": 5,          // 省略可（既定 4）。1 ループで動ける回数
  "ghosts": 1,         // 省略可（既定 1）。同時に出るゴーストの数。0〜4
  "tiles": [           // 必須。1 要素 = 1 行。文字の位置がそのまま x 座標
    "  a#",
    "S###",
    " G  "
  ],
  "objects": [         // 省略可
    {
      "type": "laser",           // 現状 "laser" のみ。未知の type は黙って無視される
      "id": "a",                 // 同じ文字の SwitchTile で無効化できる
      "position": { "x": 1, "y": 1.5 }   // 片方が .5 の半整数
    }
  ]
}
```

TypeScript の型は [src/game/stage/stagedata.ts](../src/game/stage/stagedata.ts) にある（`StageData`）。
定数（`DEFAULT_STEPS` / `MAX_COLUMNS` / `MAX_ROWS` / `PERMANENT_WALL_ID`）もそこに置いてある。

## 2. `tiles` の書き方

### 座標系

- **原点は左上。** `x` = 行内の文字位置（0 始まり）、`y` = 配列のインデックス（0 始まり）。
- 行の長さは揃っていなくてよい。足りない分はタイル無しとして扱われる。

### 使える文字

| 文字 | 意味 |
|---|---|
| `S` | スタート（**必須・1 個**）。ここにプレイヤーが出現する |
| `G` | ゴール |
| `#` | 通常タイル |
| `@` | 最初から通過済みのタイル（＝進入できない障害物） |
| `=` | **2 回まで通れるタイル。** 一筆書きの制約を局所的にゆるめる |
| `a`〜`z` | スイッチタイル。文字が ID になる |
| 半角スペース | タイル無し |
| その他の文字 | タイル無し（無視される）。ただし**小文字は必ずスイッチになる**ので注意 |

### 制約（守らないと壊れる / 崩れる）

1. **`S` は必ず 1 個入れる。** 無い場合は `(0,0)` から開始する扱いになり、
   `bun run verify` と dev サーバがエラーを出す。
   複数書いた場合は最後に見つかったものが採用される。
2. **サイズ上限**: `gap = 60px`、画面 1280x720。
   実際に使っている範囲の幅は 21 列、高さは 12 行が物理的な限界。
   **余白を考えて 18 列 x 10 行以内**を推奨。
   フィールドは自動で画面中央に寄るので、左や上に空きがあっても構わない
   （フェーズ 3 以前はずれていた。[06-known-issues.md の F-1](06-known-issues.md)）。
3. タイルが 1 個しかないステージは作らない（演出が成立しない）。

## 3. `objects` の書き方

### laser

```jsonc
{ "type": "laser", "id": "a", "position": { "x": 7.5, "y": 0 } }
```

- **`position` は必ず片方だけ `.5`。** 両方整数だとタイルの真上に乗って判定されない。
  両方 `.5` だと当たり判定のキーと一致せず機能しない。
- `x` が `.5` → タイル `(floor(x), y)` と `(ceil(x), y)` の**間**を塞ぐ（横方向の通行止め）。
- `y` が `.5` → タイル `(x, floor(y))` と `(x, ceil(y))` の**間**を塞ぐ（縦方向の通行止め）。
- 複数のレーザーに同じ `id` を付ければ、1 つのスイッチでまとめて消せる。
- **消せない壁にしたいときは `id` を `"-"` にする**（`PERMANENT_WALL_ID`）。
  `SwitchTile` の id は a-z の 1 文字なので、`"-"` は決して一致しない。
  a-z の id を書いて対応スイッチが無い場合は「書き忘れ」とみなして `bun run verify` が警告する。

> 見た目の向き（`vertical`）は `Math.round(y) === y` で自動決定される。手で指定する項目は無い。

### type を増やしたい場合

[objects.ts](../src/game/stage/objects.ts) の `objectRegistry` に 1 行足し、
[stagedata.ts](../src/game/stage/stagedata.ts) の `OBJECT_TYPES` にも足す。
手順は [04-recipes.md](04-recipes.md#レシピ-b-新しいオブジェクトギミックを追加する) を参照。

## 4. ステージの追加手順

### 4.1 ステージ順は `stages/index.ts` の配列順

ステージ順は [src/game/stage/stages/index.ts](../src/game/stage/stages/index.ts) の
`stages` 配列の並びで決まる。**ファイル名は順序に一切影響しない。**

```ts
import stage8 from "./stage8.json";   // ← 1 行足して

export const stages: Array<StageData> = [
  stage1, /* … */ stage7,
  stage8                              // ← 配列にも 1 行足す
];
```

> かつては `import.meta.glob` で読んでいたため、ファイル名の辞書順に依存しており
> `stage10.json` がステージ 2 の位置に割り込む罠があった（O-1）。フェーズ 1 で解消済み。

### 4.2 手順

1. `src/game/stage/stages/stageN.json` を作る（N は連番）。
2. §2 / §3 の制約を守って `tiles` と `objects` を書く。
3. `stages/index.ts` に **import 1 行**と**配列の 1 要素**を足す。
4. **`bun run verify` を実行する。** データの不備はここで全部出る。
5. **手で解けるか確認する**（§5 のチェックリスト）。
6. `bun run dev` で起動。前のステージまで手動で進めるのが面倒なら、
   [title.ts](../src/game/title/title.ts) の `s.load(0)` を一時的に `s.load(N-1)` に変えて確認し、**戻す**。
7. `./node_modules/.bin/tsc --noEmit` を通す。

### 4.3 検証コマンド

```bash
bun run verify
```

全ステージについて次を検査し、1 つでも問題があれば終了コード非 0 で落ちる。

- `S` がちょうど 1 個 / `G` が 1 個以上 / タイルが 2 個以上
- タイルにならない文字が混ざっていないか
- 幅 ≤ 21 列・高さ ≤ 12 行
- `steps` が 1 以上の整数か
- `ghosts` が 0〜4 の整数か
- `objects[].type` が実装済みか
- `objects[].position` が「片方が整数・もう片方が半整数」か
- `objects[].id` に対応するスイッチがあるか（`"-"` を除く）

開発サーバ（`bun run dev`）でも同じ検証が起動時に走り、`console.warn` に出る。

## 5. ステージ設計チェックリスト

**まず `bun run verify` を通すこと。** 下の前半 5 項目は自動で検査される。
残りは機械では判定できないので、頭の中（またはメモ）で追うこと。

- [ ] `S` が 1 個ある。`G` がある。 — *verify*
- [ ] 幅 21 列 x 高さ 12 行以内（余裕をみて 18 x 10 推奨）。 — *verify*
- [ ] レーザーの `position` は片方だけ `.5`。 — *verify*
- [ ] レーザーの `id` に対応するスイッチがある（恒久壁なら `"-"`）。 — *verify*
- [ ] **ループ 1 で何をさせたいか**が明確（歩数を使い切る / スイッチに乗る / 特定の位置で終わる）。
- [ ] **ループ 2 のゴーストの経路と実体歩数**を計算した（§6）。
- [ ] その結果、ゴールに到達する手順が実在する。
- [ ] 一筆書きの制約上、意図しない近道が無い。
- [ ] 詰み判定はレーザーを見ない（[02-game-rules.md §6](02-game-rules.md#6-詰み判定-isjammed)）ことを前提にしている。

## 6. ゴーストを見積もる手順

ステージ設計で最も間違えやすいのがここ。次の順で計算する。

1. ループ 1 でプレイヤーに歩かせたい経路を決める。移動回数を `u`、`steps` を `n` とする。
2. 余り歩数 `r = n - u`。ただし歩数を使い切る前に詰みやレーザーで終わる場合は、その時点の残数。
3. **次のループのゴースト**は:
   - 出発位置 = ループ 1 の**終点**
   - 経路 = ループ 1 の軌跡を**逆向きに**辿り、`S` に向かう（長さ `u` 歩）
   - **実体でいるのは、出発タイルを含めて `r` タイル分**
   - プレイヤーが 1 歩動くごとにゴーストも 1 歩動く（同期）
4. ゴーストが実体でいる `r` タイルが、ループ 2 のプレイヤーの通り道と衝突しないか（させたいか）を確認する。

```
例: steps=6、ループ1で 4 歩使って終わった場合
  r = 2 → ゴーストは「終点」と「終点の 1 つ手前」の 2 タイルだけを塞ぐ。
          残り 2 歩ぶんは半透明のまますり抜ける（ただしスイッチは押す）。
```

## 8. 既存 7 ステージの狙い（参考）

| # | tiles | steps | 教えていること |
|---|---|---:|---|
| 1 | `S###G` | 4 | 移動と一筆書きの基本 |
| 2 | `a###S###G` | 4 | スイッチとレーザー。**非実体ゴーストでもスイッチを押せる** |
| 3 | 3 行の L 字 + 縦レーザー | 5 | 縦向きレーザーと分岐 |
| 4 | 2 行、ゴールが左端 | 5 | 逆方向へ動く必要 |
| 5 | 長い横一列 + 下段 | 13 | 歩数配分。遠回りの計画 |
| 6 | 縦長 + レーザー 2 本 | 11 | スイッチ 2 個の順序 |
| 7 | 6x7 のループ状 | 10 | 総合。ゴーストの実体長を能動的に調整させる |
| 8 | 左右にスイッチ、下にゴール | 3 | **ゴースト 2 体**。2 つのスイッチを同時に押さえ続ける |
| 9 | 十字の中央が `=` | 5 | **2 回通れるタイル**。中央を 1 ループで 2 回通る（`#` だと解なし） |

新規ステージは 8 以降として、**1 つのステージで新しい概念は 1 つだけ**教える方針を踏襲すること。
